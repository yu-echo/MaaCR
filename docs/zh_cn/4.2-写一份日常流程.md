# 4.2 写一份能自己跑的日常流程

> **这一页的目标**：写出一条「**翻列表 → 遇到能领的就领 → 翻到底就收工**」的完整流程。
>
> 这是日常任务里最常用、也最值得抄的一段骨架。学会了它，
> 商店、邮件、活动页、签到页……凡是**长列表里找东西**的场景都能照搬。

## 一、为什么需要「骨架」

新手最容易写成的样子是：**一个节点管到底**（「找到免费的就领，找不到就滑一屏」）。
但框架里一个节点只能做一件事，这么写会变成：

- 节点认不到 → 卡在原地看着，等 `timeout` 走完（默认 20 秒）→ 才轮到下一个候选；
- 一屏一屏翻，翻 20 屏就白等 400 秒。

所以本项目的做法是把它拆成**三个角色**，各管一件事：

| 角色 | 干什么 | 关键参数 |
| --- | --- | --- |
| **哨兵** | 「这一屏有没有可领的？」看完立刻走，**绝不干等** | `DirectHit` + **短 `timeout`** |
| **目标** | 认到了就领掉 | `next` 指回哨兵 |
| **滑动** | 没得领就往下翻 | **`max_hit` 当滑动预算** |
| **收工** | 预算用完 / 到底了 | 干净收尾，**不报错** |

## 二、完整骨架（直接抄）

```json
    "商店扫屏": {
        "recognition": { "type": "DirectHit", "param": {} },
        "action": { "type": "DoNothing", "param": {} },
        "timeout": 1500,
        "next": ["商店领维护礼", "商店领免费项", "商店到每日精选"],
        "on_error": ["商店滑一屏", "商店扫到底"]
    },

    "商店领维护礼": {
        "recognition": {
            "type": "TemplateMatch",
            "param": {
                "template": "shop/free_label_dark.png",
                "roi": [0, 266, 720, 864],
                "threshold": 0.85
            }
        },
        "action": { "type": "Click", "param": { "target": true } },
        "post_delay": 2500,
        "next": ["商店扫屏"],
        "on_error": ["商店扫屏"]
    },

    "商店滑一屏": {
        "recognition": { "type": "DirectHit", "param": {} },
        "action": {
            "type": "Swipe",
            "param": {
                "begin": [360, 1060, 1, 1],
                "end": [[360, 340, 1, 1]],
                "duration": 1200,
                "end_hold": 300
            }
        },
        "max_hit": 60,
        "next": ["商店扫屏"],
        "on_error": ["商店扫屏"]
    },

    "商店扫到底": {
        "recognition": { "type": "DirectHit", "param": {} },
        "action": { "type": "DoNothing", "param": {} },
        "focus": "翻到底了，没有可领的 —— 跳过",
        "next": ["收尾回主界面"]
    },
```

## 三、每一处为什么这么写

### 1. 哨兵必须是 `DirectHit` + **短** `timeout`

`DirectHit` = 「永远算命中」，所以它**立刻**通过，然后开始尝试 `next` 列表。

`timeout: 1500` 是**给整个 `next` 列表的预算**：里面所有候选都认不到时，
最多试 1.5 秒就放弃、转去 `on_error`。

> ⚠️ 这两个位置**反过来的话，每屏要空等 20 秒**。
> 本项目的注释里专门记了这笔账：`post_delay` 和哨兵的 `timeout` 是**同一段等待**，
> 之前白等 1.8 秒/屏 × 60 屏 ≈ **108 秒**，接近整个任务耗时的三分之一。

### 2. `next` 的顺序 = 优先级，**但 `List` 里的顺序还有一层含义**

`next` 列表是**从上往下依次尝试，第一个认到的**胜出。所以：

- **越具体的目标越靠前**；
- **收工判据（`商店到每日精选`）必须排在最后** ——
  它一旦命中就收工，排在前面会把同一屏里还能领的东西挡掉。

### 3. `on_error` 的顺序 = 「先滑动，再收工」

```json
"on_error": ["商店滑一屏", "商店扫到底"]
```

`商店滑一屏` 是 `DirectHit`（一定命中）→ 所以正常永远轮不到 `商店扫到底`。
只有**滑动预算用完**时，`商店滑一屏` 会被跳过，才落到收工节点。

### 4. ★ `max_hit` 就是「翻几屏」的计数器

**不需要自己写累加器。** 因为：

- 这一屏**有**东西 → 走 `next` 里的目标节点 → 领掉 → 回哨兵；
- 这一屏**没**东西 → `next` 全落空 → 走 `on_error` → 滑动（消耗一次预算）。

所以「连着 N 屏没东西」**≡**「最多滑 N 次」**≡** `max_hit`。

> 顺带一提：`max_hit` 用完的节点，**在 `next` 和 `on_error` 两个列表里都会被跳过**
> （官方文档只写了 `next`，本项目 2026-09-24 探针实测 `on_error` 同样生效）。
> 所以「把收工节点排在预算节点后面」就是一套合法的「做够 N 次就收工」写法。

### 5. 滑动参数：`duration` + `end_hold` 是给识别用的

```json
"duration": 1200,     // 慢拖，别甩
"end_hold": 300       // 到终点先按住再抬手 → 消掉惯性
```

原生 `Swipe` 手速一快，列表会带着惯性继续滚 —— 而**识别只发生在停下之后**。
滚动没停就截图，等于拍糊了的照片，OCR 和模板匹配都会掉分。

`end_hold` 的作用就是「抬手时速度已经归零」，让画面在哨兵那段窗口里是**静止**的。

### 6. 别把单次滑动距离加到超过「列表可视高度」

滑动「不停下就不识别」，所以**步长 > 可视区**时，中间会有一段内容
**从没在静止状态下停留过** —— 等于漏扫。

本项目商店可视区约 790px，单次滑动取 **720px**，留足重叠。

## 四、三个必踩的坑

| 坑 | 现象 | 对策 |
| --- | --- | --- |
| **「连续 N 帧无新」当结束条件** | 会在列表半腰提前收工 | 必须**滚到底**（连续几帧滑动量实测为 0） |
| **「到底了」用帧差判** | 和「丢手势」混淆 | 判据加「连续 N 次 + 重发一次仍不动」 |
| **收工节点排在前面** | 后面更深处的东西永远扫不到 | 收工判据**永远排最后** |

> **最后一条是本项目真实踩过的**：早先有个「已收集！」提前收工节点，
> 结果当天领完后就常驻屏上，排在它下面的东西永远扫不到 —— 后来把这节点删了。

## 五、收工节点要「干净」

收工节点**只做收尾**（`DoNothing` + 回主界面），**不能是「开始乱点的兜底分支」**。

因为它会被**每一条**走投无路的路径撞上。如果它自己会点东西，
那就变成了「认不出来就乱按」—— 在付费页面上就是真金白银的事故。

本项目还额外加一条：**任何一步失败都先重新识别当前界面**（用户定的通用原则），
所以失败一律 `on_error: ["...扫屏"]`，而不是直接结束。

## 六、验收标准

1. **能翻到底**：日志里能看到滑动次数达到预算、最后落到收工节点；
2. **该领的都领到**：目标节点的命中记录（`debug/maafw.log` 里有 box + score）；
3. **跑两遍结果一致**：第二次跑不会因为「状态残留」出岔子；
4. **无 ERR**：任务以 `### All tasks have been completed ###` 收尾。
