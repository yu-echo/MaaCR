# 识别原理与调参手册

> 本项目**不用任何 OCR**，所有量化指标都是「数像素 / 量宽度 / 数色块」读出来的。
> 这份文档解释每个量怎么读、阈值怎么标、以及加新锚点时的验收标准。

---

## 一、三个量化指标（都不需要 OCR）

### 1.1 圣水（0~10）—— 「最右侧被点亮的列」

`cr_vision.read_elixir`，读 `ELIXIR_BAR = (150, 1230, 693, 1270)` 这条横带。

```python
mask = cv2.inRange(HSV(band), *H_MAGENTA)     # 洋红
lit  = (mask > 0).sum(axis=0) >= 2            # 这一列有几个点亮像素
frac = (最右侧 lit 列的索引 + 1) / 条宽
```

两个关键点，都是实测踩出来的：

1. **取「最右侧被点亮的列」，不要数像素个数**。圣水条上有白字（`10 最多:10`），
   白字会在条上打出**空洞**；数像素个数会被空洞算少，而最右边界不受影响。
2. **额外返回 `left_lit`**：条子最左端前 20 列是否连续亮。圣水是从左往右铺的，
   所以对战中左端一定亮；别的界面（比如卡组页底部导航）虽然也有一片紫色，
   但左端不会连续亮 —— 用它把误判挡掉。

### 1.2 敌方公主塔血量 —— 「血条宽度就是血量」

`cr_vision.read_enemy_towers`，读 `ENEMY_TOWER_BARS` 里两座塔的横带。

粉色的血条**宽度本身就是血量**，所以同样取「最右侧被点亮的列」
（血条上的白色数字会打出空洞，空洞不影响 min/max）：

```python
hp_frac = (最右侧 lit 列 + 1) / ENEMY_TOWER_FULL_W      # 满血基准 79px
```

血条整个消失 ⇒ 返回 0 ⇒ `_lane_broken()` 判定该路塔已破 ⇒ 落点切到敌方半场深位
（这是拿三冠的必经两步）。

### 1.3 结算皇冠数 —— 数金色色块

`cr_vision.read_crowns`。结算界面每方 3 个皇冠位：**金冠 = 已拿，蓝枕 = 没拿**。
按颜色数色块，不需要 OCR：

```python
gold = inRange(HSV(band), *H_CROWN_GOLD)
gold = morphologyEx(gold, MORPH_CLOSE, 7x7)         # 闭运算把皇冠的碎片连成一块
n, _, stats, _ = connectedComponentsWithStats(gold)
count = 面积 > CROWN_MIN_BLOB(1500) 的连通域个数
```

闭运算不能省：金冠的轮廓是镂空的，不闭运算会被数成好几块。

## 二、两个「抗误判」手法

### 2.1 状态判定必须「模板 + 颜色」双重确认

**只用颜色占比做状态判定一定会误判。** 实测：卡组页底部导航有一片亮蓝，
被误判成结算页的蓝色「确定」按钮，程序就去点了卡组页的底部导航。

所以每个状态至少要有**一个结构稳定的锚点**（模板匹配），必要时再叠一层颜色校验。
在 pipeline 里就是 `And`：

```json
"recognition": "And",
"all_of": [
  { "sub_name": "confirm", "recognition": "TemplateMatch",
    "template": "anchors/result_confirm.png", "threshold": 0.80 },
  { "recognition": "ColorMatch", "roi": [377, 1121, 190, 56], "method": 40,
    "lower": [95,120,150], "upper": [125,255,255], "count": 4256 }
]
```

`sub_name` 让第二个识别能引用第一个的框 —— 表达「在锚点命中处附近做颜色校验」。

### 2.2 白字掩码匹配（最有用的一招）

游戏 UI 文字都是「**白字 + 深色描边**」，**在任何底色上都是白的**。
所以匹配前把画面和模板**都先转成白色像素掩码**再比，等于把背景整个忽略掉：

```python
mask = cv2.inRange(HSV(img), (0, 0, 225), (180, 40, 255))    # S 低 + V 高 = 白
score = cv2.matchTemplate(frame_mask, tpl_mask, cv2.TM_CCOEFF_NORMED)
```

实测收益：

| 目标 | 白字掩码 | 原色匹配 |
| --- | --- | --- |
| 商店「免费」/「已收集！」 | 正确位置 **1.000**，14 张对照截图次高分全部 **< 0.60**（零误报） | 会被卡片底色干扰 |
| 部落「捐赠」按钮（灰） | **0.997** | — |
| 部落「捐赠」按钮（绿） | **0.898** | 只有 **0.822**，会被 0.85 阈值直接丢掉 |

⚠️ **阈值必须够严（V ≥ 225 且 S ≤ 40）**。宽松的「接近白就算」会把浅灰底（V ≈ 195）
整张卡都算成白，掩码变成一块实心区域，匹配就没意义了。
实测 `V≥225 & S≤40` 能同时干净地抠出「免费！」（白字 + 绿底）与「已收集！」（白字 + 灰底）。

**实现状态（已定案）**：这条留在 Agent，实现在 `cr_vision.find_white_text`，
调用方是 `cr_daily.py` 的商店与部落两条流程。

原本考虑过改用 pipeline 的 `TemplateMatch` + `green_mask`（把模板的非白像素涂绿），
**最后不走这条路**，三条理由：

1. 官方文档对 `green_mask` 的原文是「**应仅遮盖干扰区域，避免过度涂抹导致主体边缘特征丢失**」，
   而本项目的做法恰恰是「除了字，其余全盖掉」—— 正撞在这句警告上；
2. `green_mask` 只盖**模板侧**，画面侧仍是原色。而这两处判据的关键是「
   **双方都**只留白字」，比如「已收集！」那张卡是浅灰底（`V ≈ 195`），
   画面侧不二值化就仍然会被底色干扰；
3. 改匹配器等于把 0.898 / 0.85 这个本来就薄的余量重新标定一遍，
   而这需要实机帧 —— 见 [`daily.md` 第五节](daily.md)，本项目目前没有模拟器。

配套结论：多尺度要在**转掩码之前**缩放（先缩彩色模板、再抽白字）。
对二值掩码做插值会凭空造出一圈中间灰值，那就不是旧版实测过的做法了。

详见 `develop/migration.md` 第四节。

## 三、阈值标定

| 阈值 | 默认 | 说明 |
| --- | --- | --- |
| `MATCH_THRESHOLD` | 0.85 | 认手牌 |
| `ANCHOR_THRESHOLD` | 0.80 | 认界面锚点 |
| `RESULT_THRESHOLD` | 0.80 | 结算页「确定」（比别的严是故意的，防误判） |
| `DECK_THRESHOLD` | 0.85 | 卡组页（实测卡组页 1.00、其它画面 0.13~0.22） |
| `CHEST_THRESHOLD` | 0.85 | 开宝箱（实测宝箱屏 1.00/0.96、其它画面 0.22~0.45） |
| `NAV_MATCH_THRESHOLD` | 0.60 | 底部导航图标 |

**好消息**：MaaFramework 的 `TemplateMatch` 默认 `method = 5`（`TM_CCOEFF_NORMED`），
与旧版 `cv2.matchTemplate(..., TM_CCOEFF_NORMED)` 完全一致 ⇒ **这些阈值可以照搬**，
不用重新标定。

**坏消息**：`ColorMatch` 有两处语义差异，换算错了不会报错、只会静默失效：

1. `count` 是**像素个数**，不是占比 ⇒ `count = 占比阈值 × roi宽 × roi高`；
2. `method` 默认 **4（RGB）**，本项目全部用 HSV ⇒ 必须显式写 `method: 40`，
   且 `lower`/`upper` 的长度要与该色域的通道数一致。

## 四、加一个新锚点（或新界面状态）的流程

1. 用 MFA 工具箱 / VSCode 插件的截图功能，给这个页面**抓一帧**（720p 原生）；
2. 在页面上找一个**结构稳定、别处没有**的特征块（图标 / 特殊文字 / 边框）裁下来，
   存进 `assets/resource/image/anchors/`；
3. **回检区分度**：目标页 ≈ **1.00**，其它所有已存帧 **< 0.3** 才算合格。
   只验证「目标页能匹配上」是不够的；
4. 在对应的 pipeline 文件里加节点，或把一个已有的 `next` 候选指过去；
5. 跑 `python tools/validate.py` 确认模板路径与节点引用都对；
6. **给它一个「该做的事」**。纯粹为了「不返回 unknown」也行（至少日志更好读），
   但要想清楚：如果它没有独立动作，`next` 该回到哪里。

> 加锚点时留意：多阶段动画的界面（开宝箱）**每个阶段整体换色**，单张锚点只认得住一个阶段。
> 这时给每个阶段各存一张（本项目是 `chest_stars.png` / `chest_stars_b.png`），
> 在 pipeline 里把 `template` 写成**数组**即可（框架会取最佳，比用 `Or` 更简洁）。

## 五、手牌识别与卡组维护

`cr_vision.read_hand` 在 `HAND_ROI` 里对每张卡面模板跑一次匹配，
命中后用 `slot_of()` 把中心吸附到最近的槽位，每个槽只保留最高分。

⚠️ **同一张牌有两套素材**：普通形态 + 精英/觉醒形态，对战时会**交替出现**。
只录一套，轮到另一套那一轮就会认不出来、白白错过出牌机会。
每套卡组最多 2 个觉醒位 ⇒ **8 张牌 + 2 个精英形态 = 10 张模板**，数量固定、不会漏。

用 `CARDS` 里的 `same_as` 把精英形态关联到普通形态，`PRIORITY` 里就只用写普通形态的 id。

**漏了形态怎么办**：`CR.PlayCards` 每轮会把「认不出来的手牌槽」裁下来存到
`debug/candidates/slotN_<md5>.png`。人工认一下是哪个形态，放进 `image/cards/`
并写进 `CARDS` 即可。

⚠️ 存下来的必须是**游戏真实渲染的像素**。用 AI 生成的卡面图没用 ——
模板匹配要求逐像素对上，画得再像也匹配不上。
⚠️ 模板必须**从模拟器原生截图裁**，且**不要缩放**（缩放过的文字/卡面模板匹配会掉很多）。
