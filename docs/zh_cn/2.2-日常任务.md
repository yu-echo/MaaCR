# 日常任务：商店免费项 / 部落捐赠

> 这两条流程的判据**全部是从旧版脚本原样搬过来的**，一条都没改。
> 每一条背后都对应旧版一次实测翻车，改之前先读完这一页 —— 凭直觉「简化」一下很容易把它改回去。

代码在 `agent/cr_daily.py`，节点在 `assets/resource/pipeline/daily.json`。

---

## 一、整体形态：pipeline 管「进任务/收尾」，Agent 管「一段扫描循环」

```
商店任务 ──(CR.Boot 检查环境)──> [登录页 | 商店领免费项] ──> 日常收尾回主界面
部落任务 ──(CR.Boot 检查环境)──> [登录页 | 部落捐赠]     ──> 日常收尾回主界面
```

`登录页` 是**复用**主对战流程里已有的那一个节点（识别到就 `StopTask` + 弹提示）。
之所以能白拿：pipeline 的 `timeout` 是「**当前节点 `next` 列表的循环识别超时**」，
每一轮会把 `next` 里所有节点挨个识别一遍、命中即止 ——
所以列表里多列一个节点**不额外花时间**，代价只有一次模板匹配。

两个任务都是 `CR.Boot` 开头，不是偷懒：**屏幕熄了会让所有模板匹配变成 0.00**，
看起来像「模板全坏了」，是旧版踩过的最隐蔽的坑；`CR.Boot` 里那几行就是为它准备的。

而中间那段扫描循环留在 Agent，有四条硬原因（都不是「懒得写 JSON」）：

| 原因 | 说明 |
| --- | --- |
| 白字掩码匹配 | 画面与模板**都要**先二值化成「是不是白像素」再比。框架的 `TemplateMatch` 只有 `green_mask`，而官方文档明确写着「应仅遮盖干扰区域，避免过度涂抹导致主体边缘特征丢失」——我们的做法恰恰是「除了字，其余全盖掉」 |
| 一屏多目标 | 商店一屏上要**一次领掉所有**可见免费项，pipeline 一个节点只消费一个识别框 |
| 「滑到底」判据 | 判据是「画面**还在不在动**」，而 `wait_freezes` 是「**等**它不动」，语义正好相反 |
| 跨屏状态 | 每屏的去重集合（`seen`）+ 连续空屏计数，pipeline 里没有地方安放 |

## 二、商店：领免费项

### 判据是「免费」这两个**字**，不是颜色

用户明确说过：免费项不一定是绿卡，**但价格那里一定写着「免费」**。
先后用「圣水条洋红」和「绿底卡片」当判据都误判过，最后落到白字掩码。
细节见 [`2.1-识别原理.md` 第二节 2.2](2.1-识别原理.md)。

### 顺序：先领当前屏 → 再看「已收集！」→ 最后才导航

这三步的顺序**每一步都是坑**：

1. **先看当前屏，再导航。** 反过来的话，点底部「商店」会把页面滚回顶部，
   正好把屏幕上的免费项滑走 —— 然后才去检查就什么都找不到了。
2. **先领、再看「已收集！」。** 「已收集！」是「今天已领完」的信号，
   看到就该停（商店列表实测有 **37~55 屏**，全翻完纯属白跑）。
   但同屏可能既有没领的「免费」、又有已收集的卡，**先停后领会漏**。
3. **点卡身，不点文字。** 「免费」两字在卡片底部，直接点容易点到卡片下沿或
   网格缝隙上 —— 「点了没反应」就是这么来的，所以往上挪 `FREE_LABEL_DY = -175`。

### 领一张卡的完整时序

```
点卡身 → 等 SHOP_CARD_WAIT(2.5s) 等弹窗
      → 找绿色「免费！」按钮（**先认出才点**，原色匹配，阈值 0.85）
      → 等 SHOP_CLAIM_WAIT(2.5s) 收货动画 + 顶部横幅走完
      → 没找到弹窗：不算领到，顺手点一下底部「确定」把可能的弹窗收掉
```

> ⚠️ 「先认出才点」不能省。点完卡片到弹窗出现之间有 1~2 秒，
> 这期间如果没弹出窗，**盲点固定坐标会按到隔壁那张「500 金币」的卡上** —— 那是要花资源的。
>
> 同一个屏幕里没领到的坐标会进 `seen` 去重集合。不做这件事的话，一张点不动的卡会被反复点，
> 永远出不去这一屏。

### 「滑到底」的判据是画面静止，不是猜屏数

```
moved = |本帧 - 上帧| 的逐像素平均差        # 用 int16 相减，uint8 会回绕
连续 SCROLL_STUCK_LIMIT(3) 帧 moved < SCROLL_STUCK_DIFF(2.0)  -> 判定到底
```

实测滑到底后 `moved` 从 ~45 掉到 ~0.2，区分度极大。
兜底判据是 `SHOP_IDLE_LIMIT = 60`（连续 60 屏没找到「免费」就收工）与硬上限 120 屏。

> ⚠️ 这条是**为什么必须在自定义动作里真实重新截图**的原因。
> 框架的 `controller.cached_image` 是「上一次识别时留下的那一帧」，
> 连着取两次会拿到同一张图 → 第一屏就会判成「画面静止 / 到底」，整条流程空转结束。
> 所以 `MaaDriver.shot()` 走的是 `post_screencap()`。见 `cr_nodes.MaaDriver.shot`。

## 三、部落：捐赠

### 三个关键点（旧版用户报 bug 后改出来的）

1. **必须找全部「捐赠」按钮，不能只取评分最高的那一个。**
   聊天里可能同时有「自己发起的请求」（按钮**灰的**、捐不了）和「别人的请求」
   （按钮**亮绿色**、可以捐）。旧实现只取最优，正好撞上灰的那个 →
   判「不可捐」直接收工 → **一个都没捐出去**。

2. **匹配必须忽略按钮底色。**
   模板是从灰按钮上裁的，绿按钮底色完全不同：拿整按钮做原色匹配，
   绿按钮只有 **0.822**（低于 0.85 阈值，会被直接丢掉）。
   换成白字掩码后，「捐赠」两个字在任何底色上都是白的：

   | | 白字掩码 | 原色 |
   | --- | --- | --- |
   | 灰按钮（捐不了） | **0.997** | — |
   | 绿按钮（可捐） | **0.898** | **0.822** ← 会被丢掉 |

3. **可捐 / 捐不了的判据是按钮底色的饱和度，不是绿色占比。**
   实测同一帧里两个按钮：自己发起的底色纯灰 `S = 0.0`，别人的亮绿 `S = 142.3`，
   区分度极大 ⇒ `DONATE_LIT_SAT = 60`。绿色占比只写进日志方便对照，不参与判断。

### 点一下就直接捐出，没有二次确认弹窗

```
点绿色「捐赠」按钮 → 立刻捐出（飘 +10 金币 / +50）→ 按钮随即变灰
```

所以「捐完要点确定」是**错的**：底部那个蓝色「确定」是**退出聊天**的按钮。
每捐一次就点它一下 = 捐完一次就退出，永远捐不了第二次。
⇒ 只在**全部捐完之后**点它一次。

### 进聊天页也要容错

在部落聊天子页里，底部导航条被输入条（请求换卡 / 友谊战…）和「确定」盖住，
导航模板匹配只有 **0.00**。所以走 `Nav.goto` 的容错路径：导航条看不见、
但底部有个「确定」按钮时，点它清理界面再试。全部失败才退回「直接看当前屏」。

## 四、怎么调

| 想改什么 | 改哪里 |
| --- | --- |
| 一次进部落最多捐几次 | 界面上的「部落最多捐几次」，或 `cr_config.DONATE_ROUNDS`（默认 4） |
| 当前屏没可捐请求时往上翻几层 | `DONATE_LOOK_SCREENS`（默认 8） |
| 「免费」两字的匹配严格程度 | `FREE_LABEL_THRESHOLD`（默认 0.78） |
| 点卡身时往上挪多少 | `FREE_LABEL_DY`（默认 -175） |
| 滑动快慢与每屏等待 | `SHOP_SCROLL` / `SHOP_SCROLL_WAIT`（必须**慢滑**，商店内容是懒加载的） |
| 判定「可捐」的饱和度门槛 | `DONATE_LIT_SAT`（默认 60） |
| 换日 / 换活动后认不出「免费」 | 重采 `image/shop/free_label.png`（**从模拟器原生截图裁，不要缩放**） |

## 五、⚠️ 还没实机验证

这两个任务和主对战一样，**一次都没有在真实模拟器上跑过**（开发环境没有模拟器）。
离线检查（`tools/validate.py`、官方 schema 校验、`py_compile`）全部通过，但那只能证明
「引用没写错」，证明不了「认得准」。

第一次跑请务必：

1. 跑「日常一条龙」，看日志里
   `发现 N 处「免费」` / `看到 N 个「捐赠」按钮，其中可捐(亮绿) N 个` 的数字对不对；
   （**它会真的点** —— 本版本已去掉演练模式开关，所以数字不对就立刻停下来查。）
2. 数字对了就让它跑完；
3. 顺带盯一眼这两件事（它们是这次移植里语义最不确定的地方）：
   - `MaaDriver.shot()` 每次真的是新帧吗 —— 看「第 N 屏」的日志有没有正常递增，
     如果第一屏就报「画面已静止（差 0.00），判定到底」，说明截帧这一步没生效；
   - 「免费！」弹窗按钮的原色匹配在真机上够不够 0.85（弹窗底色理论上固定，但没实测过）。

其余待验证项（自愈重置语义、`ColorMatch.count` 换算、坐标系）见
[`3.2-迁移对照.md` 第五节](3.2-迁移对照.md)。
