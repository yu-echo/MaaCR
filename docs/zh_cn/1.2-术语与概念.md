# 1.2 术语与概念

看日志、改 pipeline、翻框架文档时会撞到的词。左边是通用叫法，右边是**它在这个项目里具体指什么**。

## 框架侧（MaaFramework / MFAAvalonia / MaaPiCli）

| 词 | 是什么 |
| --- | --- |
| **MaaFramework** | 底层自动化框架：负责截图、识别、执行动作。本项目跑在它上面 |
| **MFAAvalonia** | 通用**图形界面**（一个 .NET 程序）。它读 `interface.json` 决定显示哪些任务与选项 |
| **MaaPiCli** | 官方**命令行**客户端，跑同一份 `interface.json` + `resource/`，但没有界面。见 [1.1-快速开始](1.1-快速开始.md) |
| **Controller / 控制器** | 「怎么操作设备」。本项目用 `Adb` 控制器，连 MuMu 的 `127.0.0.1:<端口>` |
| **Resource / 资源包** | `assets/resource/`：模板图 + pipeline JSON + OCR 模型 |
| **Tasker / Context** | 跑任务的执行体与上下文。本项目**没有**用它的自定义能力（见下） |
| **Pipeline / 流水线** | 一串 JSON 节点。每个节点 = 一次「识别」；认到了就执行动作、再走向 `next` |
| **节点（node）** | pipeline 里的一个 JSON 对象，有名字，比如 `对战中`、`结算界面` |
| **`next`** | 当前节点识别成功**之后**要走的候选节点列表，**有序**（按误判代价排） |
| **`on_error`** | 当前节点的 `next` 循环识别**超时**、或动作失败时去哪 |
| **`max_hit`** | 这个节点最多被识别成功多少次。用满之后，**它在别人 `next` / `on_error` 列表里会被跳过**——本项目拿它当「次数预算」用 |
| **`timeout`** | ⚠️ 不是「这个节点的超时」，而是「当前节点 `next` 列表的循环识别超时」 |
| **Custom 识别 / 动作** | 框架自带算法表达不了的逻辑，用 Python 写好后注册进去。**本项目：0 个** |
| **Agent** | 跑 Custom 代码的那个 Python 进程。**本项目：没有** |
| **`interface.json`** | ProjectInterface V2 协议文件：告诉客户端有哪些任务、哪些选项、各自覆盖哪些节点 |
| **`pipeline_override`** | 界面选不同选项时，往流水线节点上盖的补丁。本项目的选项**全靠它生效** |
| **`green_mask`** | 匹配时把模板里不关心的部分涂绿从而跳过。**只作用于模板侧**，且只给 TemplateMatch / FeatureMatch |
| **`color_filter`** | OCR 的颜色处理：填一个 ColorMatch 节点名，先按它的色域二值化再送 OCR。本项目「认白字」靠它 |
| **`cached_image`** | 框架缓存的那一帧，是**上一次识别时**留下的，不等于当前画面 |

## 本项目侧

| 词 | 是什么 |
| --- | --- |
| **环境准备** | pipeline 里的一条链：点屏常亮（`Shell`）→ 拉起游戏（`StartApp`）→ 清障 → 等主界面。**不是**外部脚本 |
| **主界面锚点** | 「主界面『对战』按钮那片橙色」的色块判据。它是**启动链的终点**，之后去哪儿由各任务的 `pipeline_override` 决定 |
| **三级自愈** | 认不出界面时的兜底阶梯：① 点底部导航回主界面 → ② 当全屏弹层点 → ③ 重启游戏（`StopApp` + `StartApp`） |
| **白字掩码** | 一个只做颜色二值化的 `ColorMatch` 节点（`白字掩码`），被 OCR 的 `color_filter` 引用 —— 游戏 UI 文字都是「白字 + 深色描边」，按「够白」筛一遍就把底色整个忽略掉 |
| **扫屏 / 扫到底** | 本项目扫描循环的两个固定角色：「扫屏」短超时试一次，没试到就滑动；滑动预算用满就落到「扫到底」节点收工 |

## 五个最容易搞反的语义

这几条都是逐字读框架文档 / 实测确认过的，改动相关逻辑前先读一遍：

1. **`timeout` 不是「这个节点的超时」**，而是「当前节点的 **`next` 列表**的循环识别超时」。
   三个推论：
   - 往 `next` 里多塞一个候选节点**不额外花时间**（每轮按顺序全试一遍，命中就停）；
   - **反过来说**：如果你想让某一步「先判断、不中就做别的」，就别把判断节点塞进 `next`
     —— 它会被循环识别 20 秒（默认）才放弃。要短超时判断就用 `timeout` 压下来。
   - ⚠️ 这一条踩过：商店「滑一屏 → next: [找免费]」写反了，导致「翻到底」从来没真正生效。
2. **`next` 列表为空 = 任务终止**（协议明写的终止条件）。所以任何一个「这一支走到头」的节点，
   如果 `next` 忘了接，流程会静默结束 —— 看起来像「任务莫名跑完」。
   本项目踩过最狠的一次：任务走到 `主界面锚点` 后 `next` 是空的，**商店/部落任务一次都没跑到自己的逻辑**。
3. **`max_hit` 用满的节点，在别人的 `next` 和 `on_error` 两个列表里都会被跳过**（实测确认）。
   本项目「扫到底就跳过」就是靠这个：把终点节点排在预算节点后面。
4. **`green_mask` 只盖模板侧，且不适用于 OCR**。本项目认「免费 / 捐赠 / 已收集」这些白字
   走的是 OCR + **`color_filter`**（协议原生的颜色二值化），不是 `green_mask`。
5. **`cached_image` 不能当当前画面**：它是上一次识别留下的一帧，不等于此刻屏幕。
