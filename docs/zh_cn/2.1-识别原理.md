# 识别原理与调参手册

> 本项目是**纯 JSON 流水线**：所有判断都由 MaaFramework 的内置识别算法直接表达，
> 没有自定义识别、没有脚本。这份文档讲：用了哪几种算法、每种怎么算分、
> 阈值怎么标、加新锚点时的验收标准。

---

## 一、只用了 4 种识别算法

| 算法 | 用在哪 | 怎么算分 |
| --- | --- | --- |
| `TemplateMatch` | 界面锚点、手牌卡面、导航图标 | `cv2.matchTemplate(..., TM_CCOEFF_NORMED)`，取最高分，**和 OpenCV 完全一致** |
| `ColorMatch` | 「圣水够不够」「塔破没破」「是不是主界面」 | `cvtColor(method) → inRange(lower, upper) → countNonZero`，比的是**像素个数** |
| `OCR` | 商店「超值推荐」标签、部落「捐赠」/「确定」 | PP-OCRv5（`model/ocr/` 里那三个文件），比的是**文本相似度** |
| `DirectHit` | 「这一步不用认，直接做」的节点 | 永远命中（用它做闸门、自环、兜底） |

再加两个组合器：

- **`And`**：全部子识别都命中才算命中。**这是本项目的防误判主力**（见 §二）。
- **`Or` / `inverse`**：`Or` 任一命中即可；`inverse` 把结果取反。

**⚠️ 没有任何「量化读数」**。旧版脚本会去数「圣水条最右侧被点亮的列 → 0~10 费」，
纯 JSON 做不了这种几何计算，所以现在全部退化成**阈值判断**：

| 旧版读法 | 现在 |
| --- | --- |
| 圣水 = 最右侧亮列 ÷ 满条宽 | 「够不够出牌」= 在一个 **6px 宽**的小 roi 上比颜色（`出牌-圣水够`，roi `[581,1230,6,40]`） |
| 敌方塔血 = 血条宽度 | 「这路塔破没破」= `落点-破塔深位` 在 `[138,166,8,30]` 上比颜色，**加了 `inverse`**（认出「没有血条」才成立） |
| 皇冠数 = 金冠色块个数 | 不用数了 —— 结算界面只判「到没到」（`And`，见下） |

这个退化是**有意的**：能表达的部分就用阈值，表达不了的不硬做。

## 二、防误判：`And` 双重确认 + 有序 `next`

### 2.1 状态判定必须「模板 + 颜色」双重确认

**只用颜色占比做状态判定一定会误判。** 实测：卡组页底部导航有一片亮蓝，
被误判成结算页的蓝色「确定」按钮，程序就去点了卡组页的底部导航。

所以状态节点是 `And`，一个结构锚点（模板）叠一层颜色校验：

```jsonc
"结算界面": {
    "recognition": {
        "type": "And",
        "param": {
            "all_of": [
                { "sub_name": "confirm",
                  "recognition": { "type": "TemplateMatch",
                                   "param": { "template": "anchors/result_confirm.png",
                                              "threshold": 0.8 } } },
                { "recognition": { "type": "ColorMatch",
                                   "param": { "roi": [377, 1121, 190, 56], "method": 40,
                                              "lower": [95, 120, 150], "upper": [125, 255, 255],
                                              "count": 4256 } } }
            ],
            "box_index": 0
        }
    }
}
```

`sub_name` 让后面的识别能引用前面命中框的位置；`box_index: 0` 指定最终对外用第 0 个子识别的框。

### 2.2 ⚠️ `ColorMatch` 最坑的一点：「整屏同色」会饱和假命中

`count` 比的是**像素个数**，所以当某一屏**整屏都是那个颜色**时，
roi 里的计数会直接**饱和到 roi 的总面积**——看起来「命中得比平时还满」。

实测踩过（2026-09-24）：`主界面锚点` 判的是底部橙色「对战」按钮
（roi `[244,934,250,64]`，`count` 阈值 8000，正常值 **13203**）。
结果游戏停在**开宝箱的整屏橙色动画**上时，那个 roi 里全是橙色 →
`count = 250 × 64 = 16000`（满格）→ **假命中**，框架以为到主界面了，
后面全在错的屏上瞎撞（`商店去商店页` 连试 21 次 0.2882，20 秒后任务失败）。

**指纹**：同一批锚点同时失效，且分数「整体偏低」**或者**「整体饱和」。
（偏低 = 有遮罩压暗；饱和 = 整屏同色。两种都要怀疑「画面本身不对」，不要去调阈值。）

### 2.3 `next` 列表的顺序 = 优先级

`next` 是**按顺序逐个识别、命中第一个就执行**。这等价于旧版的 `if / elif` 链，
而且**判定顺序按「误判代价」排**，不是随便写的：

```
结算界面 → 登录页 → 奖励宝箱 → 对战中 → 卡组页 → 主界面 → 匹配中 → 未知界面处理
```

结算排第一，是因为误判会让程序点错按钮（左边紧邻「再来一场」，点错直接再开一局）。

**`next` 里必须有一个「一定会命中」的节点**（`DirectHit`），否则整条链会超时结束。
主循环把 `未知界面处理` 放在末尾就是这个道理。

> `timeout` 是「**当前节点 `next` 列表的循环识别超时**」，不是「本节点自己的超时」。
> 官方原话：调整本节点识别等待时间应改**上一节点**的 timeout。
> 推论：**`next` 里多列一个节点不额外花时间**（命中即止），所以「顺手多查一个界面」是白拿的。

## 三、阈值标定

| 用在哪 | 阈值 | 实测区分度 |
| --- | --- | --- |
| 手牌卡面 | **0.85** | 目标 ≈ 1.00，其它卡面 < 0.5 |
| 界面锚点 | **0.80** | 目标 ≈ 1.00，其它画面 < 0.6 |
| 结算页「确定」 | **0.80** | 比别的严是故意的，防误判 |
| 卡组页 | **0.85** | 卡组页 1.00、其它画面 0.13~0.22 |
| 开宝箱（橙屏） | **0.80** | 橙屏 ≥ 0.9985 / 其它画面 ≤ 0.5750（2026-09-24 重标，见下） |
| 底部导航图标 | **0.60** | 选中态图标会加宽并位移，跟未选中态模板对不上，所以放到 0.6 |
| OCR 文本 | **0.30** | PP-OCR 的相似度尺度跟模板匹配不是一回事，0.3 已经够严 |

**好消息**：`TemplateMatch` 默认 `method = 5`（`TM_CCOEFF_NORMED`），
与 `cv2.matchTemplate(..., TM_CCOEFF_NORMED)` 完全一致 ⇒ **阈值可以照搬**，不用重标定。

**坏消息**：`ColorMatch` 有两处语义差异，换算错了不会报错、只会静默失效：

1. `count` 是**像素个数**，不是占比 ⇒ `count = 占比阈值 × roi宽 × roi高`；
2. `method` 默认是 **4（RGB）**，本项目全部用 HSV ⇒ 必须显式写 `method: 40`，
   否则那三个 HSV 数字会按 RGB 解释，判据全失效。

> ⚠️ **换模板必须重新标定，不能只测「新模板认不认得出目标」**。
> 2026-09-24 就踩过：给开宝箱橙屏加节点时，顺手复用了现成的
> `chest_stars.png` / `chest_stars_b.png`，**没验它们实际得分**。
> 事后离线复算：这两张在三张橙屏截图上最高只有 **0.571**（阈值 0.85）——
> 从来没命中过，那个节点等于白加。**验收必须正负样本都算分。**
> 这两张废模板已于同日**从仓库删除**；`recover.json` 里那处引用也一并
> 换成了实测锚点 `chest_orange_stars.png` / `chest_orange_slots.png`（阈值 0.8）。

## 四、加一个新锚点（或新界面状态）的流程

1. 给这个页面**抓一帧原生截图**（720×1280，用 MFA 工具箱 / VSCode 插件 / `adb exec-out screencap`）；
2. 在上面找一个**结构稳定、别处没有**的特征块（图标 / 特殊文字 / 边框）裁下来，
   存进 `assets/resource/image/anchors/`；
3. **回检区分度 —— 这是最关键的一步**：
   - 在**目标页的所有帧**上都跑一遍（动画会有多帧，最低分才算数）；
   - 在**手头所有别的页**上也跑一遍（最高分才是威胁）；
   - 合格线：**目标页最低分 ≥ 0.85，其它页最高分 < 0.6**，且两者余量越宽越好。
     只验证「目标页能匹配上」是**不够的**。
   > 离线复算可以直接用 `cv2.matchTemplate(..., TM_CCOEFF_NORMED)` —— 和框架算法完全一致。
4. 在对应的 pipeline 文件里加节点，或把一个已有的 `next` 候选指过去；
5. **核对两件事**（原来 `tools/validate.py` 会查，那个脚本已随「去 Python」删除，现在只能人工）：
   - `template` 的**路径真的存在**（写错 = 识别永远 0.00，不报错）；
   - `next` / `on_error` 里的**节点名真的存在**（写错 = 静默失联，不报错）；
6. **给它一个「该做的事」**。纯粹为了「不返回 unknown」也行（至少日志更好读），
   但要想清楚：如果它没有独立动作，`next` 该回到哪里。

> **多阶段动画的界面要给每个阶段存模板**，`template` 写成**数组**即可
> （框架会取最佳，比用 `Or` 简洁）。开宝箱那一屏就是靠
> `chest_orange_stars.png` + `chest_orange_slots.png` 两个特征互相兜底。

## 五、手牌识别与卡组维护

`对战中` 节点的 `And` 里有两条：**圣水条亮**（`ColorMatch`）+ **手牌有牌**（`TemplateMatch`
在 roi `[108,1011,712,1267]` 里对全部卡面模板跑一次，命中即算）。

出牌靠 `出牌-圣水够` 的 `next` 列表顺序：

```
出-木质船 → 出-斗笠持刀 → 出-光头大笑 → 出-绿飞龙 → 出-蓝色亡灵 → 出-绿哥布林 → 出-火焰怪 → 出-白骨
```

**从上往下试第一张「在手」的牌** —— 这就是出牌优先级。

「什么时候出牌」= `出牌-圣水够` 那个 `ColorMatch` 的 roi **起点 x**：
`581` 对应「攒到 8 费再出」，往左挪 x 就是降低门槛（圣水条是从左往右铺的）。
界面上的「对战策略」下拉就是改这个 x。

⚠️ **同一张牌有两套素材**：普通形态 + 精英/觉醒形态，对战时会**交替出现**。
只录一套，轮到另一套那一轮就会认不出来、白白错过出牌机会。
每套卡组最多 2 个觉醒位 ⇒ **8 张牌 + 2 个精英形态 = 10 张模板**，数量固定、不会漏。

**漏了形态怎么办**：看 MFAAvalonia 的识别可视化，把认不出的那一槽截图裁下来，
放进 `image/cards/` 并在 `battle.json` 加一个 `出-xxx` 节点、挂进 `出牌-圣水够.next`。

⚠️ 存下来的必须是**游戏真实渲染的像素**。用 AI 生成的卡面图没用 ——
模板匹配要求逐像素对上，画得再像也匹配不上。
⚠️ 模板必须**从模拟器原生截图裁**，且**不要缩放**（缩放过的文字/卡面模板匹配会掉很多）。
