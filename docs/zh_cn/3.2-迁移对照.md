# 从旧版脚本迁移到 MaaFramework：语义对照与既有经验

> 这份文档原本还包含「模块去向」和「待实机验证清单」两节，
> 那是**纯 JSON 化之前**（还有 Python Agent 那会儿）的状态。
> 现在 Agent 与全部脚本都已经删掉，那两节随之作废 ——
> 这里只留**仍然成立**的两块：**框架语义陷阱** 和 **框架无关的既有经验**。
>
> 旧版 `crbot`（自写 OpenCV + adb + PyQt6）与 MaaCR 是**同一套识别资产**在两种架构下的实现；
> 理解它的 if/elif 链怎么变成 `next` 列表，是读懂现在这套流水线的最快路径。

---

## 一、核心思维转换：if/elif 链 = next 有序列表

这是整个迁移最关键的一条。旧版 `vision.analyze()` 是**按固定优先级**逐条判断、返回第一个命中的状态；
MaaFramework 的 `next` 列表是**按顺序**逐个识别、命中第一个就执行。**这两件事是同一个东西。**

```
旧版 analyze() 判定顺序                现在的 对战循环入口.next
──────────────────────────────────      ─────────────────────────────
1. result_confirm + 蓝色双重确认    →   结算界面          (And)
2. cadpa 锚点（登录页）             →   登录页            (TemplateMatch)
3. chest_stars*（多阶段动画）       →   奖励宝箱          (TemplateMatch，实测锚点 chest_orange_*)
4. 手牌 ≥ 2 张 或（≥1 张 且圣水左端亮）→ 对战中            (And)
5. deck_slots（卡组页）             →   卡组页            (TemplateMatch)
6. 主界面「对战」按钮橙色占比        →   主界面            (ColorMatch)
7. cancel（匹配中）                 →   匹配中            (TemplateMatch)
8. 全部未命中                       →   未知界面处理      (Or / DirectHit，三级自愈)
```

⚠️ **判定顺序必须原样保留**，它是按「误判代价」排的，不是随便写的。
（结算排第一，因为误判会让程序点错按钮 —— 左边紧邻「再来一场」，点错直接再开一局。）

另外注意现在**多了一个排在很前面的 `[JumpBack]关掉卡牌已收到弹窗`** ——
它是「模态弹窗 + 半透明遮罩会把整批背景锚点同时压暗」这个坑的解法：jump_back 会在
它自己跑完后回到父节点重扫，所以一个节点能服务多个上下文。

## 二、字段语义对照（容易踩的地方）

| 旧版写法 | MaaFramework | 注意 |
| --- | --- | --- |
| `cv2.matchTemplate(..., TM_CCOEFF_NORMED)` | `TemplateMatch` | `method` 默认就是 5，与 cv2 一致 ⇒ **阈值可照搬**，不用重标定 |
| `Device.screenshot()`（每轮真截一张） | 框架每次识别自己截 | ⚠️ 别把 `controller.cached_image` 当「当前画面」—— 它是**上一次识别时**留下的那一帧 |
| `_frac(frame, box, HSV_RANGE) > 0.40` | `ColorMatch` | ⚠️ `count` 是**像素个数**不是占比，必须 `阈值 × roi宽 × roi高`；例 `0.40×190×56 = 4256` |
| `cv2.COLOR_BGR2HSV` | `ColorMatch.method: 40` | ⚠️ 默认是 **4（RGB）**，不显式写就按 RGB 解释你的 HSV 三元组，判据全失效 |
| `time.sleep(n)` | `post_delay: n` | |
| `while matches_done < N` | 节点的 `max_hit` | `max_hit` = 「最多命中 N 次，用尽后在其他节点的 `next` 里被跳过」；**这是纯 JSON 唯一能用的计数器** |
| `nav.goto()`「处理完再重试」 | `"[JumpBack]节点名"` | 语义完全对应 |
| `restart_game()` | `StopApp` / `StartApp` 两个纯 JSON 节点 | |
| 自写 `Logger`（控制台 + 文件双写） | 框架 `debug/maafw.log` + 节点的 `focus` 字段 | `focus` 的值会显示在通用 UI 的日志区 |
| 失败时存截图 | `save_on_error` / `save_draw` | 默认失败会往 `debug/on_error/` 存一张带时间戳的截图，**排障第一手材料** |

### ⚠️ `timeout` 的语义极易搞错

pipeline 的 `timeout` 是「**当前节点 `next` 列表的循环识别超时**」，不是「本节点自己的超时」。
官方文档原话：**调整本节点识别等待时间应改上一节点的 timeout**。近似逻辑：

```
while (!hit && !timeout) { foreach (next); sleep_until(rate_limit); }
```

两个直接推论，日常任务的设计就是靠它们才成立的：

1. **`next` 列表里多列一个节点不额外花时间** —— 每一轮会把整张列表挨个识别一遍、
   命中即止。所以「日常任务入口也顺手查一下登录页」是白拿的（代价只有一次模板匹配）。
2. **`next` 里必须有一个「一定会命中」的节点，否则整条链会超时结束。**
   主循环把 `未知界面处理`（含 `DirectHit`）放在 `next` 末尾就是这个道理。

`on_error` 的触发条件是「本节点 `next` 列表**超时未命中**」或「动作执行失败」——
注意是**本节点**的，不是子节点的。

### ⚠️ 协议里没有跨节点累加器，也没有时钟

- **计数只能靠 `max_hit`**（用一次少一次）。所以只能表达「最多重复 N 次」，
  表达不了「累计到 N」（比如「累计捐满 40 张卡」写不出来）。
- **`timeout` 不是任务级时间预算**（每次回到该节点都会重置），所以
  「累计运行 N 小时」这种判据**做不到**。日常循环的轮数也因此**不放在流水线里** ——
  它由客户端的「重复次数」控件给（见 `interface.json` 的「日常循环」任务），只按**轮数**，不按时间。
  原因见下一条。
- **`max_hit` 是「一次任务运行内」的额度，用完不重置** —— 所以「每轮打几局 × 跑几轮」
  在流水线里乘不出来（填 3 局 × 3 轮会变成第一轮连打 9 局、后两轮跳过战斗）。
  交给客户端重复就没有这个问题：每重复一次 = **新的一次任务运行**，额度自然归零。

## 三、pipeline JSON 不写注释（历史约定，现已放开）

官方 sample 与多数社区项目的 pipeline 都是**纯 JSON**，所以最早本项目也不在 pipeline 里写 `//`，
把设计理由放在文档和 Python 注释里。

**现在 Python 没了，理由无处可放，所以 pipeline 里开始写 `//` 注释了。**
MaaFramework 的解析器接受带注释的 JSON（`interface.json` 官方模板本身就带注释），
本项目现在两处都写 —— 注释里重点记「**这个参数为什么是这个值**」和「**踩过什么坑**」。

## 四、别丢掉的既有经验

这几条是旧版踩出来的、**框架无关**的结论，改流程时别改回去：

1. **状态判定必须「模板 + 颜色」双重确认。** 只用颜色占比一定会误判 ——
   实测卡组页底部导航有一片亮蓝，被误判成结算页的蓝色「确定」按钮，程序就去点了卡组页的导航。
2. **判定顺序按「误判代价」排。**
3. **绝不按返回键兜底。** 返回键会弹出游戏自己的「要退出吗」对话框，越「恢复」越乱。
   要重置就用 `StopApp`（force-stop）。
4. **「认不出来」≠「卡住」。** 加载 / 开宝箱动画都属于「认不出来但画面一直在变」，那是正常的；
   只看时间的话冷启动（13 秒以上）会被无限重启。
5. **导航「找不到」≠「不存在」。** 选中态的图标会加宽并位移，跟未选中态模板对不上 ——
   这时正确动作是**判到达**，不是按返回键。（所以底部导航模板的阈值才放到 0.6。）
6. **新坐标一律程序化量取 + 画框人眼复核**，不要肉眼估（实测偏差能到 100px）。
7. **每个写死坐标都要在注释里写清「这个数是量出来的、换分辨率要重量」**。
8. **模板必须从模拟器原生截图裁**，不要用手机截图缩放（缩放过的文字模板匹配会掉很多）。
9. **「点了没反应」是最难查的一类失败**（坐标落在两行按钮中间的空隙上，点了等于没点还不报错）。
   解法就是第 6 条 —— 且**别直接点文字**，文字常写在卡片下沿，`target_offset` 往上挪一点才落在卡身内。
10. **静态检查通过 ≠ 能跑。** 现在连静态检查脚本都没有了，更要靠**真机跑一遍 + 看日志的命中链**。

## 五、现在怎么定位问题（替代原来的「待验证清单」）

原来那份「我无法离线验证、需要上机逐条过」的清单已经全部实际验过了。现在的排障路径是：

1. 看 `debug/maafw.log` 里的**命中链**：每个节点命中时会写
   `reco hit [result.name=xxx]`，串起来就是它实际走的路；
2. 不复预期就找**没命中**的那个节点的 `reco [result={...}]` 行，
   里面带 `score` / `count` 与框位 —— 这是最直接的证据；
3. 任务失败时看 `debug/on_error/` 里那张带时间戳的截图，**它就是失败当场的画面**；
4. 想复算某个分数，直接用 `cv2.matchTemplate(..., TM_CCOEFF_NORMED)` / `inRange` + `countNonZero`
   手工算一遍 —— 与框架数值**完全一致**（本项目多次用它确认过）。

**判据的指纹**：同一批锚点**同时**失效 → 不是阈值问题，是**画面本身不对**。
- 分数**整体偏低** → 有半透明遮罩压暗了（弹窗）；
- 分数/计数**整体饱和** → 整屏同色（例如开宝箱的整屏橙色，`ColorMatch` 会直接吃满 roi）。
