# 4.3 挂到界面上并验证

> **这一页的目标**：把写好的流程**变成界面上可勾选的任务**，然后**真的跑起来**。
>
> 到这一步你已经有能跑的节点了，但用户点不到它 ——
> 因为 `interface.json` 才是「界面长什么样」的定义。

## 一、`interface.json` 是什么

它定义三件事：

| 字段 | 管什么 |
| --- | --- |
| `controller` | 用什么设备（本项目是 Adb） |
| `resource` | 资源包（模板图 + 流水线）在哪 |
| `task` | **界面上有哪些任务可勾**，每个任务从哪个节点开始跑 |

`interface_version: 2` 是固定必填。

## 二、加一个任务

```json
{
    "name": "领商店礼包",
    "entry": "商店任务",
    "default_check": true,
    "description": "打开商店，把能白拿的东西领掉。",
    "option": ["领取内容", "商店翻几屏"]
}
```

| 字段 | 意思 |
| --- | --- |
| `name` | 界面上显示的任务名 |
| `entry` | **入口节点名**，必须和 pipeline 里某个节点**逐字一致** |
| `default_check` | 默认勾不勾 |
| `description` | 界面上鼠标悬停/点问号时显示的说明 |
| `option` | 这个任务暴露哪些可调项（见下一节） |

### ★ 最容易漏的一步：把启动链接到你的入口上

本项目所有任务都从 `环境准备`（一个 `DirectHit` 节点，永远命中）开始走启动链，
最后停在 `主界面锚点`。而 `主界面锚点` 的 `next` 默认是**空的** ——
协议里 `next` 为空 = 任务终止。

**所以不接这一根线，任务会在到达主界面后就结束，你的流程一次都跑不到。**

接法是在任务上用 `pipeline_override`：

```json
{
    "name": "领商店礼包",
    "entry": "商店任务",
    "pipeline_override": {
        "主界面锚点": { "next": ["商店去商店页"] }
    }
}
```

> `pipeline_override` = 「**只对这个任务**，把某个节点的某些字段改掉」。
> 同一份 pipeline 被多个任务复用，各自接不同入口，靠的就是它。

## 三、加一个可调项（option）

四种常用类型：

```json
"option": {
    "商店翻几屏": {
        "type": "input",
        "label": "商店最多翻几屏",
        "description": "最多往下翻几屏。",
        "inputs": [
            { "name": "屏数", "label": "屏数", "default": "60",
              "pipeline_type": "int", "verify": "^[1-9][0-9]*$" }
        ],
        "pipeline_override": {
            "商店滑一屏": { "max_hit": "{屏数}" }
        }
    },

    "要对战的策略": {
        "type": "select",
        "label": "对战策略",
        "default_case": "稳健推进",
        "cases": [
            { "name": "稳健推进" },
            { "name": "有费就出",
              "pipeline_override": { "出牌-圣水够": { "param": { "roi": [0, 1060, 240, 20] } } } }
        ]
    }
}
```

`pipeline_override` 是**深合并** —— 只写你要改的那几个字段，其余保留，
所以上例里 `出牌-圣水够` 的 `recognition` 类型、阈值这些都不用重写。

### ⚠️ 两条硬规矩

**1. `interface.json` 里绝对不能出现 `setting` 字段。**

MFAAvalonia 点「开始任务」时会抛 `Call from invalid thread`，
然后**任务锁被永久占住** —— 点停止也没用，只能重启软件。

所以本项目的做法是：**把「设置」散到每个任务自己的 `option` 里**，不用全局 `setting`。

**2. `pipeline_override` 里写的节点名必须真实存在。**

覆盖一个不存在的节点**不会报错**，只会静默无效 —— 表现为「这个选项点了没用」。

## 四、验证：改完必须真跑

**这个项目现在没有静态自检脚本**（原来那个是 Python 写的，随「去 Python」删掉了）。
所以**改 pipeline / interface.json 没有任何自动拦截** —— 写错了就是「界面上少一个任务」
或者「某个选项没反应」，而不会报错。

验证走这三步：

### 第 1 步：无头实跑（最关键的验证）

用 `MaaPiCli.exe -d` 直接跑（不用开界面）：

```bash
# 工作目录必须是含 interface.json 的项目根
MaaPiCli.exe -d
```

⚠️ 两个常见坑：

- **`config.adb.name` 必须和设备枚举结果里的 `name` 逐字一致**，
  否则控制单元创建失败（日志里 `screencap_methods=0`）。
  别手写配置，**先用交互模式跑一次让它自己写**。
- 模拟器多开 / 多个 adb server 时，确认选中的是**你要那台**。

### 第 2 步：看识别可视化图

跑完看 `debug/vision/*.jpg` —— **框架自己看到的那一帧 + 识别框 + 分数**，
文件名带节点名。它能直接回答：

- 框架看到的是哪个界面？
- 识别框画在哪、分多少？
- 命中之后界面变成了什么？（看下一个节点的图）

### 第 3 步：看日志

```bash
# ⚠️ debug/maafw.log 是跨运行累积的，一定要带日期前缀
grep -a "2026-09-30" debug/maafw.log | grep -a "你的节点名"
```

`TemplateMatcher::analyze` 那行会给出 `all_results_` / `best_result_`（含 box 和 score），
标定和诊断都用它，不必自己重跑 OpenCV。

## 五、交付前：出包

发布包不是把仓库原样压缩 —— 布局不一样：

```
MFAAvalonia 的 win-x64 发布包（平铺在包根）
  + 本仓库的 assets/resource/      →  包根/resource/
  + 本仓库的 assets/interface.json（去注释、改 version）
  + 使用说明.md
  → zip
```

**三个容易忘的点**：

1. `interface.json` 必须和 `MFAAvalonia.exe` **同层**，`resource/` 也是；
2. `interface.json` 里 `icon` 引用的图标要一起放进去，否则界面静默用回默认图标；
3. **组装完的目录不要先双击开一次再打包** ——
   MFAAvalonia 首次启动会改包（删 `MaaAgentBinary/`、建 `agent/`、
   写出 `appsettings.json` / `backup/` / `temp/` / `logs/` / `debug/`），
   打进去的就是「已经被改过」的包。

## 六、一句话总结

> **`entry` 要对上节点名、`pipeline_override` 要把主界面锚点接到你的入口、
> 别用 `setting`、改完必须用 `MaaPiCli -d` 真跑一遍再看 `debug/vision/` 的图。**
>
> 这四件事做到，你的流程才算「写完了」。
